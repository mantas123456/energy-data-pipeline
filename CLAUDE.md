# Notes for Claude Code

ENTSO-E electricity data pipeline for Lithuania: API → PostgreSQL → SQL marts → quality
checks → day-ahead load forecast → report committed back to the repo by GitHub Actions.

## Layout
- `src/energy_pipeline/entsoe.py`: API client and XML parser (A03 compression, mixed PT15M/PT60M)
- `src/energy_pipeline/db.py`: SQLAlchemy tables, idempotent upsert, runs `sql/*.sql` in name order
- `src/energy_pipeline/sql/`: SQL models (PostgreSQL dialect). Tables are rebuilt on each run.
- `src/energy_pipeline/quality.py`, `forecast.py`, `pipeline.py` (steps), `cli.py` (`pipeline` command)
- `config.yaml`: zones, series, check thresholds
- `data/observations/<zone>/<series>/<year>.csv.gz`: committed raw data, written by the daily job
- `reports/`: generated by `pipeline report` / `pipeline daily`

## Commands
- `pip install -e ".[dev]"`, then `docker compose up -d` for PostgreSQL
- `pytest`: integration tests need `DATABASE_URL` (see `.env.example`); otherwise they skip
- `ruff check . && ruff format .` before committing; CI enforces both
- `pipeline backfill --start YYYY-MM-DD`, `pipeline daily`, `pipeline report`, `pipeline check --strict`

## Rules
- Store timestamps in UTC; only convert to local time in SQL marts and reports.
- Forecast features must not use load newer than `MIN_LAG_H` (48 h). Keep the leakage test passing.
- Never commit `.env` or the API key. GitHub uses the `ENTSOE_API_KEY` secret.
- Don't hand-edit `data/` or `reports/`; they are generated.
- Report results honestly. If the model loses to the TSO forecast, say so.
